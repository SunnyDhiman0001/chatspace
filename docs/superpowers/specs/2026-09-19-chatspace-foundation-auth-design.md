# ChatSpace — Foundation + Auth Phase Design

Date: 2026-09-19

## Overview

ChatSpace is a full-stack Flutter chat/social portfolio app on Firebase Spark
(free) plan. This spec covers the first two of six build phases:

1. **Foundation** — Firebase setup, folder skeleton, core packages, DI, shared
   widgets/theme, base abstractions.
2. **Auth** — signup/login (email+password, Google), splash/session routing.

Later phases (Profile, Chat list, 1-1 Chat, Push notifications) are out of
scope here and get their own spec when reached.

## Tech Stack

- Flutter (latest stable)
- Firebase Auth, Cloud Firestore, Firebase Storage, Firebase Cloud Messaging
- State management: **Bloc/Cubit** + **flutter_hooks** (chosen over Riverpod —
  Cubit's sealed-state-class model fits the "abstract class State extends"
  pattern the app uses throughout; hooks handle local widget state like
  controllers)
- No `copyWith` state pattern: every state is its own class extending an
  abstract base state, using `Equatable` for value equality
- Error handling: custom `Result<T>` sealed class (no `dartz` dependency)
- DI: `get_it`
- Routing: `go_router`

## Firebase Setup Steps

1. Create Firebase project in console. Analytics left off (not needed for
   free-tier lean scope).
2. Authentication → Sign-in method → enable Email/Password and Google.
3. Cloud Firestore → create database, production mode, pick a region.
4. Storage → get started, production mode, same region as Firestore.
5. Cloud Messaging is auto-enabled with the project; no extra toggle.
6. Run `flutterfire configure` to generate `firebase_options.dart` and
   register Android/iOS/web apps (creates `google-services.json` /
   `GoogleService-Info.plist` automatically).
7. Android: minSdkVersion 23+, `google-services` Gradle plugin (handled by
   flutterfire configure).
8. iOS: enable Push Notifications + Background Modes (remote notification)
   capability in Xcode.
9. Google Sign-In: register SHA-1/SHA-256 fingerprints (Android) and URL
   scheme (iOS) in Firebase console — exact steps walked through during Auth
   implementation.
10. Firestore/Storage security rules are written per-phase, not left open.
    This phase ships the `users` collection rules (see below).

## Firestore Data Structure

```
users/{uid}
  uid: string
  displayName: string
  email: string
  photoUrl: string | null
  fcmToken: string | null
  createdAt: timestamp
  lastSeen: timestamp

chats/{chatId}                       # chatId = sorted "uidA_uidB"
  participantIds: [uidA, uidB]
  participantInfo: {
    uidA: { displayName, photoUrl },
    uidB: { displayName, photoUrl }
  }
  lastMessage: string
  lastMessageAt: timestamp
  lastMessageSenderId: string
  unreadCount: { uidA: number, uidB: number }

chats/{chatId}/messages/{messageId}
  senderId: string
  type: "text" | "image"
  text: string | null
  imageUrl: string | null
  createdAt: timestamp
  status: "sent" | "delivered" | "read"
```

- `chatId` is a deterministic sorted uid pair to avoid duplicate chat docs and
  let the client compute the doc ref without a query.
- `participantInfo` and `unreadCount` are denormalized onto the chat doc so
  the Home screen needs a single query (no N+1 reads per contact).
- Read receipts: the recipient's client sets message `status` to `"read"`
  when the chat is opened (batched write) and decrements their own
  `unreadCount` entry on the chat doc.

Storage layout:

```
profile_pictures/{uid}.jpg
chat_images/{chatId}/{messageId}.jpg
```

## Push Notification Approach (Spark-compatible)

No Cloud Functions on Spark plan, so there is no server-side Firestore
trigger to fan out pushes. Approach: after the sender's client writes a
message document, it directly calls the FCM HTTP v1 API (using a bundled
service-account key via `googleapis_auth`) to push a notification to the
recipient's stored `fcmToken`. This works even if the recipient's app is
killed.

**Security caveat**: bundling a service-account key in the client exposes it
to reverse engineering. Acceptable for a portfolio/demo app; documented in
the README as a known limitation with the upgrade path (move the send call
into a Cloud Function once/if the project moves to Blaze plan).

This mechanism is implemented in the Push Notifications phase (not this
spec), but the `fcmToken` field on `users/{uid}` is created during Auth so
later phases don't need a schema migration.

## Foundation Phase — Deliverables

- Firebase initialization in `bootstrap.dart`.
- `get_it` DI registration: Firebase SDK instances, repositories, use cases,
  and cubits registered as factories/lazy singletons.
- `go_router` configured with a redirect guard based on auth state (splash →
  login/home).
- Shared `core/`: `Result<T>` (`Success<T>` / `Err<T>`), `Failure` abstract
  class + subclasses, `UseCase<Type, Params>` abstract base, shared widgets
  (button, text field, loading indicator, error view).
- App theme (colors, text styles).

## Auth Phase — Deliverables

- **Domain**: `AppUser` entity; `AuthRepository` interface; use cases
  `SignUpWithEmail`, `SignInWithEmail`, `SignInWithGoogle`, `SignOut`,
  `WatchAuthState`.
- **Data**: `AuthRemoteDataSource` wrapping `FirebaseAuth` +
  `GoogleSignIn`, and creating the `users/{uid}` Firestore doc on first
  sign-up/sign-in; `UserModel` (`fromFirebaseUser`); `AuthRepositoryImpl`
  catching `FirebaseAuthException` and mapping to `Failure` subclasses,
  returning `Result`.
- **Presentation**: `AuthCubit extends Cubit<AuthState>`. `AuthState` is an
  abstract class with subclasses `AuthInitial`, `AuthLoading`,
  `AuthAuthenticated(AppUser)`, `AuthUnauthenticated`, `AuthError(String
  message)` — each its own class extending `AuthState`, using `Equatable`,
  no `copyWith`.
- **Pages**: `SplashPage` (watches auth state, routes to login or home),
  `LoginPage`, `SignupPage` — built as `HookWidget`s using `flutter_hooks`
  for `TextEditingController`s/`FocusNode`s, wrapped in
  `BlocBuilder`/`BlocListener` for cubit state.
- **Firestore rules (users collection)**: a user can read/write only their
  own doc; other authenticated users can read (needed for chat-list display
  in a later phase); no unauthenticated access.

## Testing Checkpoint

Run the app, sign up with email, confirm a `users/{uid}` Firestore doc is
created, sign out, sign back in with Google, confirm the splash page routes
correctly based on auth state.

## Constraints / Conventions

- Every file kept under 300 lines.
- No `StatefulWidget` — use `HookWidget`/`HookConsumerWidget`-equivalent
  (`flutter_hooks` with `flutter_bloc`) instead.
- No `copyWith` on state classes — each state variant is its own class
  extending the feature's abstract base state.
- Repository pattern strictly separates data layer (Firebase SDK calls) from
  domain layer (business logic, entities, use cases).
